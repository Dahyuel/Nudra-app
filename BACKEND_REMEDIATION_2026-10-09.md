# Nudra backend remediation report

Date: 9 October 2026. Scope: non-payment remediation from `BACKEND_AUDIT_NON_PAYMENTS_2026-10-09.md`, plus the interim Paymob-style course checkout mock. Real Paymob integration remains deferred.

## Result and release decision

The confirmed access, reset-race, async-process-crash, progress/certificate, enrollment-capacity, socket-revocation, readiness and restore defects have code fixes and passing local regressions. The course payment mock is implemented, visibly simulated, owner-bound and idempotent. Live production configuration disables it; an explicitly isolated demo is supported.

**Do not treat this as an unrestricted public-launch approval.** A target VPS and its credentials/DNS, independent backup destination, external alert destination and live provider verification were not available. Remaining operational gates and narrower limitations are listed below. A passing local test does not establish production throughput, real delivery, successful TLS issuance or complete vulnerability absence.

The local development configuration points `backend/.env` to the existing local PostgreSQL container (`127.0.0.1:5432/nudra`), matching the root `.env` and `nudra-postgres` Compose service. A protected custom-format backup was taken before schema work and validated with `pg_restore --list` (`/tmp/nudra-local-migration/before.dump`, mode 0600); its SHA-256 companion is present and verifies. The local schema was missing the baseline `organizations` and `org_memberships` tables and the `organization_manager` role value; the exact baseline tables/value were restored, then all 21 migrations through `0020_rls_default_deny.sql` were applied. The complete chain was first exercised against a restored database copy. Counts remained 7 users, 5 courses, 36 lessons, 4 enrollments, and 3 orders; the expected 16 catalog items were imported from existing labels. The live database now tracks all 21 migrations. The previously configured Supabase project was not touched. A future VPS deployment still needs its own intentional data-transfer and migration plan. Existing user frontend/dashboard/landing work was preserved.

## Data and lifecycle changes

New migrations `0015`–`0019` add authoritative video duration/activity, persisted exam assignments, mock-event provenance, encrypted email outbox, object cleanup tasks, security auditing, admin MFA, storage accounting, verified email/session state and database-triggered realtime revocation. Applied SQL checksums are enforced; reviewed legacy history adoption must be explicit. SQL migrations are authoritative and `db:push` is removed.

Organization owner/account/membership creation, instructor invitations and course/section creation now commit related records atomically. Reset, signup/welcome, enrollment, mock fulfillment and certificate email jobs commit with their domain operation. Outbox delivery has leases, bounded retries and provider idempotency keys. Provider delivery itself is not inside a database transaction. Some community/decision notifications remain best effort.

Curriculum changes reconcile learning state transactionally. Courses with enrollment/booking/order history cannot be hard-deleted through the ordinary route; attempted quiz deletion/replacement with result history is refused. Deferred object cleanup retries and reports failure. Retention windows and upgrade effects are documented in `ops/VPS_RUNBOOK.md`. A complete account export/deletion workflow and business-approved privacy retention policy are not invented by this remediation.

## Interim Paymob mock

`paymob_mock` creates orders from server course prices, persists simulated terminal events and grants an online course enrollment only through transactional finalization. Controls support success, failure, cancellation and expiry. Duplicate/concurrent success cannot create duplicate entitlements; canceled enrollment reactivates deliberately. The UI states that no money is charged and requests no card/CVV data. Order status is loaded from the server.

Production hosted simulation requires `APP_MODE=demo`, a separate database ending `_demo`, `MINIO_BUCKET_PREFIX=nudra-demo`, separate demo storage identity, and explicit tester emails. The live template uses `PAYMENT_PROVIDER=disabled`, `APP_MODE=live`. Unknown providers do not fall back to successful simulation. Client-selected online booking payment stays pending.

This is a product mock, not Paymob's official sandbox/API contract. Booking mock settlement, real gateway credentials/callback verification, reconciliation/refunds, full booking financial history and the deferred monetary-validation findings are not counted as resolved.

## Remaining release gates and material limitations

1. Qualify the full final Compose stack on the intended VPS, including fresh image pulls/builds, real root/tenant TLS issuance and dependency readiness. Provision production administrator MFA and configuration keys before login.
2. Update or rebuild the selected maintained SILO release against a Go toolchain that fixes `CVE-2026-78667` and `CVE-2026-97031`, then rescan server and bundled client. The currently pinned image reduces the archived-MinIO findings substantially, but retains these two HIGH findings in both binaries; CI intentionally fails on them. I could not safely rebuild locally: there is no Go toolchain installed, the Go 1.27.2 builder image pull stalled, and both SILO and its bundled `mcli` client must be replaced and qualified together. SILO's [published release](https://github.com/pgsty/silo/releases) still uses Go 1.27.1; no unverified binaries were substituted. The official [MinIO repository](https://github.com/minio/minio) is archived. Before a production storage change, back up, migrate on a copy, check object integrity and exercise rollback. |
3. Complete image/OS/FFmpeg vulnerability scans and handle actionable findings. Application npm advisories alone do not scan these layers. Refresh pinned digests through a tested update procedure.
4. Configure an independent encrypted offsite repository and externally delivered alerts. Perform a matching database-plus-object restore on a clean target and record actual RPO/RTO. Local copies/journal alerts do not satisfy this gate.
5. Verify real mail sender configuration/delivery/retry/bounce handling and real AI/transcription/embedding provider compatibility. Preserve the configured 768-dimensional embedding contract and existing model provenance; model changes may require re-embedding.
6. Benchmark the actual VPS with simultaneous playback/upload/transcoding/AI/backups; set capacity from latency, errors, resource use and queue age. Inventory/backfill legacy media quotas. Complete target-device streaming/seek/disconnect tests and representative query plans.
7. Keep one API instance until distributed room broadcasts/connection caps are qualified. Retain authenticated private-media delivery; do not make HLS/raw public to solve performance.
8. Agree on account export/deletion and retention policy, legacy certificate communication and whether email verification should become mandatory. These are explicit product decisions with data-migration effects.

Operational commands, configuration, MFA provisioning, demo isolation, migration adoption, retention, backups and restore procedure are in `ops/VPS_RUNBOOK.md`. The original audit files remain historical evidence; this document describes the remediation working tree and its practical verification boundary.
